Ursache: `moin-kark` ist ein **privates** Repo. Auf öffentlichen Repos ist
GitHub Actions unbegrenzt kostenlos, auf allen Runner-Typen; die 2.000 Minuten
gelten nur für private. Dort zählt **macOS zehnfach**, Windows doppelt, Linux

Kontingent.

## Apple-Zertifikate: braucht deine Entscheidung

Ein anderer Agent (Konfi Quest) hat gewarnt, dass iOS-Release-Builds im Konto
Zertifikate anhäufen. **Nachgeprüft: stimmt, und Moin Kark ist mitverantwortlich.**

**Ursache.** `-allowProvisioningUpdates` erlaubt Xcode, fehlende Anmeldedaten
selbst über die ASC-API anzulegen. Der Keychain eines CI-Runners ist bei jedem
Lauf leer — also entsteht pro Build ein neues Development-Zertifikat. Die Option
steht in `ios-release.yml` an **zwei** Stellen (Zeile 131 beim `archive`, 162
beim `exportArchive`), was die Zahl verdoppelt.

Das Limit gilt **kontoweit**, nicht pro App: Läuft es voll, kann keines der
Projekte mehr bauen — und Xcode am Mac auch nicht.

**Stand im Konto (24.09., vor Build 71):**

```
DISTRIBUTION      Simon Luthe       bis 2026-11-28  D22NVZMW4W   <- echt
IOS_DEVELOPMENT   Simon Luthe       bis 2027-01-20  YZJUFGXDQ5   <- echt
DEVELOPMENT       Created via API   bis 2027-09-23  X3L9U6C6VA   <- Wegwerf
DEVELOPMENT       Created via API   bis 2027-09-24  256B53882G   <- Wegwerf
DEVELOPMENT       Created via API   bis 2027-09-24  8LF95YX929   <- Wegwerf
DEVELOPMENT       Created via API   bis 2027-09-24  9MTV47KBRU   <- Wegwerf
```

Die drei mit Ablauf 2027-09-24 stammen von den Läufen dieser Nacht. (Das
Ablaufdatum ist Anlage-Datum + 1 Jahr — damit lässt sich jedes Zertifikat einem
Tag zuordnen.)

**Messung nebenbei:** Ein Lauf, der erst am Upload scheiterte, hat trotzdem ein
Zertifikat angelegt; ein mitten im Archiv abgebrochener nicht. Das Zertifikat
entsteht also beim **Signieren**. Der Befund hat dem anderen Agenten seinen
Fehler gelöst — er hatte die Option ebenfalls zweimal drin, obwohl sein
Kommentar das Gegenteil behauptete.

**Zweiter Befund: Das App-Store-Profil ist kaputt.**

```
INVALID  IOS_APP_STORE  "Moin Kark AppStore 2"  erstellt 2026-06-18  bis 2026-11-28
```

Es referenziert genau ein Zertifikat — `D22NVZMW4W`, das lebt. Es fehlt also
nichts; die Ursache liegt vermutlich darin, dass ein Lauf ein konkurrierendes
Profil fürs selbe Bundle angelegt hat. Ein INVALID-Profil lässt sich nicht
reparieren, nur neu anlegen (`POST /v1/profiles`, altes vorher löschen — der
Name ist belegt).

**Was zu tun wäre, in dieser Reihenfolge:**

1. Die vier `Created via API`-Zertifikate löschen (`DELETE /v1/certificates/<id>`).
   Die beiden „Simon Luthe" behalten.
2. Profil `Q6B9P3GQ4S` löschen und neu anlegen.
3. Vorfeld im Workflow bauen — bei uns fehlen **zwei von drei** Teilen:
   - Distribution-`.p12` im Keychain: ✅ vorhanden
   - App-Store-Profil als Datei auf dem Runner: ❌ fehlt
   - `CODE_SIGN_STYLE = Manual` + `CODE_SIGN_IDENTITY = "Apple Distribution"` +
     `PROVISIONING_PROFILE_SPECIFIER` in der **Release**-Konfiguration der
     `project.pbxproj`: ❌ steht auf `Automatic` / „iPhone Developer"
4. Erst dann `-allowProvisioningUpdates` an beiden Stellen entfernen.
5. Vorher/Nachher-Zahl messen.

**Nichts davon ausgeführt.** Alle Schritte sind schreibende, unumkehrbare
Eingriffe in ein Konto, an dem mindestens drei Projekte hängen — und der andere
Agent arbeitet parallel daran. Nachts nebeneinander her Profile zu löschen wäre
genau der Weg, nach dem sich niemand mehr zurechtfindet. Das gehört in **eine**
abgestimmte Aktion.

**Achtung bei Punkt 3, aus fremder Erfahrung:** Die Signiereinstellungen gehören
in die Projektdatei, **nicht** auf die `xcodebuild`-Kommandozeile. Dort gelten
sie für jedes Ziel im Workspace, auch für jeden Pod, und der Build bricht mit
„FirebaseSessions does not support provisioning profiles" ab.
